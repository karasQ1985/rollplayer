没有完全覆盖。 上一套设计原则可以作为 HTML 页面播放器的基础，但不能直接照搬 Qt 桌面播放器的事件处理方案。

HTML 页面播放器有一套独立的交互机制，尤其需要额外考虑：

1. 浏览器原生滚轮事件与页面滚动之间的冲突。
2. `wheel` 事件的捕获、冒泡和默认行为。
3. 鼠标悬停区域与 DOM 元素的关系。
4. 触控板连续滚动与普通鼠标滚轮的差异。
5. 浏览器页面缩放快捷操作的保护。
6. 视频播放器全屏、画中画和动态 DOM 状态。
7. HTML 原生 `input[type="range"]` 滑块的兼容性。
8. 浏览器自动播放策略与音频状态同步。

如果目标是开发一个长期维护的 HTML5 视频播放器，我建议将设计扩展为以下 Web 专用方案。

## 一、HTML 页面播放器的事件设计

HTML 中主要使用：

```
element.addEventListener("wheel", handler, {
    passive: false
});
```

这里有一个关键细节：

`passive: false` 允许事件处理程序调用 `event.preventDefault()`，阻止浏览器执行默认滚动行为。

但不能无条件阻止所有滚轮事件。

推荐规则：

| 鼠标所在位置 | 滚轮行为        |
| ------ | ----------- |
| 音量滑块   | 调整音量        |
| 音量图标   | 调整音量        |
| 视频画面   | 遵循播放器既定交互策略 |
| 播放列表   | 正常滚动列表      |
| 页面其他区域 | 正常滚动页面      |
| 播放进度条  | 遵循进度条自身规则   |

核心原则：只有明确属于音量控制区域的滚轮事件，才允许进入音量处理逻辑。

## 二、必须正确处理 deltaMode

这是 HTML 实现中非常容易被忽略的问题。

浏览器的 `WheelEvent` 提供三个滚动单位：

| deltaMode         | 含义 | 处理方式          |
| ----------------- | -- | ------------- |
| `DOM_DELTA_PIXEL` | 像素 | 按像素灵敏度换算      |
| `DOM_DELTA_LINE`  | 行  | 转换为标准滚轮单位     |
| `DOM_DELTA_PAGE`  | 页面 | 单独处理，避免一次调整过大 |

不能假设 `event.deltaY` 永远代表标准的120单位滚轮增量。

另外，按住 Ctrl 滚动通常用于浏览器页面缩放，应该直接排除，不能误触音量控制。MDN 对这些事件差异有明确说明。

## 三、HTML 音量控制的推荐架构

DOM Wheel Event

接收鼠标、触控板滚动事件

Wheel Normalizer

deltaMode、方向、设备增量归一化

Volume Controller

统一管理音量、静音、边界与步进

HTMLMediaElement

video.volume / video.muted

UI Synchronizer

range、音量图标、OSD、状态反馈

这里有一个重要的浏览器兼容性问题：

`HTMLMediaElement.volume` 虽然是标准接口，但 MDN 将其标记为非 Baseline，因为部分主流浏览器不支持通过该属性进行正常的程序化音量控制。

[image](https://www.google.com/s2/favicons?domain=https://developer.mozilla.org\&sz=32)

MDN



因此，不能简单认为所有浏览器都能通过：

```
video.volume = 0.5;
```

获得完全一致的行为。

如果目标是桌面 Chrome、Edge、Firefox 等环境，可以优先采用原生媒体音量接口，并进行实际兼容性测试。如果还要覆盖移动 Safari 等环境，需要单独设计音量控制能力检测和降级策略。

## 四、HTML 实现必须额外遵循的规则

| 规则        | 推荐方案                           |
| --------- | ------------------------------ |
| 事件绑定      | 绑定到音量控制容器，而不是整个 document       |
| 事件监听      | `addEventListener("wheel")`    |
| 默认行为      | 仅在有效音量操作时调用 `preventDefault()` |
| 被动监听      | 需要取消默认行为时使用 `passive: false`   |
| 事件传播      | 避免重复监听和重复处理                    |
| Ctrl + 滚轮 | 不处理                            |
| 水平滚轮      | 不处理                            |
| 设备识别      | 不强行根据滚轮数值猜测设备类型                |
| 滑块        | 使用 `input[type="range"]`       |
| 状态同步      | 监听 `volumechange`              |
| 组件卸载      | 移除事件监听器                        |
| 全屏        | 保持相同的音量控制逻辑                    |
| 画中画       | 与原播放器音量状态保持一致                  |

特别强调：`volumechange` 事件非常有价值。它可以让滑块和音量图标跟随媒体元素的实际音量、静音状态变化，而不只是跟随鼠标事件。

## 六、还需要明确一个影响架构的重要问题

你所说的 HTML 页面播放器，可能有两种不同的产品形态：

1\. 播放器的实现形式

完全自定义播放器（HTML + CSS + JavaScript）

基于原生 video 标签，外部自定义控制栏

使用 Video.js、Plyr、MediaElement.js 等成熟播放器框架

2\. 主要运行环境

Windows 桌面浏览器（Chrome / Edge / Firefox）

移动端浏览器（Android / iOS）

桌面与移动端都需要支持

Electron / WebView 嵌入式播放器

确认开发场景

确定这两个条件后，就可以针对实际环境制定完整的技术规范，而不是简单移植桌面播放器的事件逻辑。
